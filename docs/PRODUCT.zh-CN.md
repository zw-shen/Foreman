# Foreman 产品与功能定义

## 1. 产品定义

Foreman 是一个 **git-backed 的 AI coding agent 监工看板**。

它解决一个具体问题：agent 说"我做完了"，但你无法判断这句话是真的。
Foreman 的做法是绕过 agent 的自我汇报，直接检查任务 repo 里真实发生的 commit，
核对 agent 写在约定位置的完成/失败信号，并要求一份结构化的交接文档（而非流水账）。

**使用者**：同时指挥多个 coding agent、需要快速判断"哪个任务真的推进了、哪个在原地打转"的开发者。

## 2. 非目标

- **不是调度系统。** Foreman 不启动 agent、不管理进程生命周期、不做并发控制或任务认领。
- **不是 agent 运行时。** 不代理、不转发、不拦截 agent 与模型之间的请求。
- **不写目标 repo。** Foreman 只读目标 repo 的 git 历史与信号文件。
  连 `TASK.md` 这类任务文件也由 agent 按提示词里的规范自己创建，Foreman 不代写。
- **不做数据库。** 无 DB，状态全部来自 git 和信号文件。
- **不设运行超时。** 任务可以无限期运行，Foreman 不因为"太久没动静"就判定失败。

Foreman 自己写的东西只有：任务定义、任务基线、拼接出的提示词，全部落在自己的 `data/` 目录里。

## 3. 核心原则：声明 ≠ 事实

| | 来源 | 可信度 |
|---|---|---|
| **声明态** | agent 写进约定位置的信号文件 | 不可信，仅作为线索 |
| **核实态** | Foreman 从 git 历史推导 | 事实 |

看板必须同时展示两层。当两层冲突时，冲突本身就是最重要的信息。

## 4. 状态模型

### 4.1 声明态（agent 写入约定位置，Foreman 去读）

每个任务自己把状态写到约定路径，Foreman 只负责按约定去读，不干预写入过程。

| 值（JSON 键名） | 看板显示 | 含义 | 人要做什么 |
|---|---|---|---|
| `working` | 进行中 | agent 正在干活 | 不用管 |
| `done` | 完成 | 整个任务干完了，agent 不打算继续 | 去核实 |
| `awaiting_review` | 完成等待验收 | 阶段性完成，agent 想要人点头再继续 | 去看代码、给结论 |
| `awaiting_input` | 等待回答 | 卡住了，有问题必须先回答才能继续 | 去回话 |
| `failed` | 失败 | agent 放弃，必须附 `reason` | 去看原因 |

`awaiting_review` 和 `awaiting_input` 是原「完成等待回复」拆开的结果 ——
两者要人做的动作完全不同（看代码 vs 回问题），拆开后看板上一眼就知道该干嘛，不必点进去。

`done` 与 `awaiting_review` 的区别在于 agent 是否还打算继续：前者收工，后者等放行。

失败原因由 agent 自己写，Foreman 不做二次 LLM 诊断。

### 4.2 核实态（Foreman 推导，不信 agent）

| 值 | 看板显示 | 判定依据 |
|---|---|---|
| `verified` | 已验证 | 声明 `done`，且基线之后有真实 commit，且交接文档校验通过 |
| `unsubstantiated` | 存疑 | 声明 `done`，但无 commit / 无实际 diff / 交接文档缺必填段落 |
| `contradicted` | 自相矛盾 | 声明 `failed` 但存在可观的 commit（活儿可能能捞），或反之 |

### 4.3 最后活动时间（不做判定）

不设超时状态。但每个任务显示**最后活动时间** —— 最近一次 commit 或信号文件更新距今多久
（例如"2 小时前"）。

这是有意的取舍：agent 崩溃或死循环时不会自己写 `failed`，看板上它和一个正常长跑的任务无法区分。
硬超时会制造假警报，所以 Foreman 不替你下结论，只把"多久没动静"摆出来，判断交给人。

## 5. 任务创建与提示词

任务在**前端新建**，这同时解决了"Foreman 怎么知道要盯哪个 repo"的问题 ——
登记 repo 和新建任务是同一个动作。

Foreman 不启动模型。使用者自己开一个大模型会话，把 Foreman 生成的提示词贴进去。

### 5.1 新建任务填写项

| 字段 | 说明 |
|---|---|
| 任务目的 / 目标 | 必填 |
| 背景信息 | |
| 验收标准 | 核实态判定的依据之一 |
| 能做 / 不能做 | 约束 |
| 目标 repo | 有默认值，可选「使用已有设置」 |
| 记忆 repo | 有默认值，可选「使用已有设置」 |
| 知识库 | 有默认值，可选「使用已有设置」 |

所有 repo / 路径类字段都提供**「使用已有设置」**：候选值来自历史任务里用过的值，
从下拉里选即可，不必每次重敲，也不额外维护一份全局默认配置。

### 5.2 知识库

知识库是**多文件**的，存放在私有 repo 中（通过 §6 的约定位置接入），
基础知识与项目知识**并列**：

```
knowledge/
├── base/       # 基础知识：跨项目通用（技术栈偏好、代码风格、通用约束、常用命令等）
└── projects/   # 项目知识：按项目组织
```

两个关键设计：

- **按需读取，不全量注入。** 提示词里不塞知识库全文，只给出**索引**（有哪些条目、各自讲什么）
  和知识库路径，由 agent 自己判断需要哪几篇再去读。避免上下文被无关内容占满。
- **增量生长。** 跟 agent 聊的过程中，遇到值得沉淀的信息，按需要把它写成新条目加进知识库。
  知识库因此是活的，不是一次性配置完就冻结。

### 5.3 提示词由四部分拼接

1. **知识库索引** —— 条目清单 + 各自一句话说明 + 知识库路径，agent 按需自取（§5.2）
2. **任务信息** —— 目的、背景、验收标准、约束
3. **仓库信息** —— 目标 repo、记忆 repo、知识库位置
4. **协作规范** —— 固定段落，由 Foreman 保证每个任务都带上

第 4 部分是整套约定能否落地的关键。因为 Foreman 不写目标 repo，
所有信号文件都得靠 agent 自己按规范创建，所以提示词里必须讲清楚：

- 信号文件写在哪个路径（§7）
- 每个文件的格式要求，`STATUS.json` 的字段和取值
- **什么时候更新状态**：每完成一步就更新，不要攒到最后
- 完成 / 等待验收 / 等待回答 / 失败分别该写哪个值
- 失败时必须写清原因
- `HANDOFF.md` 的必填段落，以及"不要写成流水账"
- **知识库怎么用**：先看索引，只读需要的条目，不要全量读
- **什么时候往知识库写**：聊的过程中出现值得沉淀的通用信息，
  按需写成新条目放进 `base/` 或对应项目目录

### 5.4 基线 commit

新建任务时，Foreman 记录目标 repo 当前的 HEAD 作为**基线**。
之后"哪些 commit 属于这个任务"就有了确定答案：**基线之后的 commit**，
无需猜测或依赖 commit message 约定。这是核实引擎能成立的前提。

## 6. 存储

无数据库。目录结构上把「代码」和「私有数据」彻底分开：

```
Foreman/
├── src/            # 应用代码（入库）
├── docs/           # 文档（入库）
├── .gitignore
└── data/           # ← 整个目录 gitignore，私有数据挂载点
    ├── memory/     # link 到私有记忆 repo
    ├── knowledge/  # link 到私有知识库 repo，内含 base/ 与 projects/
    └── tasks/      # 任务数据：JSON + Markdown
```

私有仓库（记忆、知识库）通过**在约定位置放一个链接**接入，
所以它们的远程地址、内容都不出现在本公开仓库里。
`data/` 已整体加入 `.gitignore`，避免误提交把私有信息带出去。

## 7. 信号文件约定

早期草案有 7 个文件，过多。收敛到 4 个：

| 文件 | 内容 |
|---|---|
| `TASK.md` | 任务契约：背景、目标、验收标准、能做/不能做 |
| `TODO.md` | 活的清单，checkbox 形式 |
| `STATUS.json` | 机器可读状态 + 失败原因 |
| `HANDOFF.md` | 结构化交接文档 |

砍掉的：

- `TODO.md` + `DONE.md` → **合并为 `TODO.md`**，用 `- [ ]` / `- [x]`。两个需要保持同步的文件是 bug 温床。
- `PROGRESS.md` → **删除**。它正是"流水账"的来源，且与 git log 重复。
  Foreman 直接渲染 commit 历史，比 agent 手写的进度叙述更可信。
- `CONSTRAINTS.md` → **并入 `TASK.md`** 的一个段落。

路径约定，随目标 repo 的代码一起被 git 跟踪：

```
<目标 repo>/.foreman/tasks/<task-id>/
```

好处：信号本身进了 git，**状态变更历史免费获得**，而且难以伪造 ——
agent 想谎报"一直都很顺利"，得连 commit 历史一起编。

### 7.1 `STATUS.json`

```json
{
  "task_id": "string",
  "state": "working | done | awaiting_review | awaiting_input | failed",
  "updated_at": "ISO-8601",
  "reason": "state 为 failed 时必填，由 agent 自己写",
  "question": "state 为 awaiting_input 时必填，写清在等什么"
}
```

不设"agent 自报 commit 列表"字段：commit 归属由基线推导（§5.4），不采信 agent 的说法。

`question` 字段让"在等什么"直接显示在看板上，人可以当场回话，不必点进去翻。

### 7.2 `HANDOFF.md` 防流水账模板

从 7 段精简到 5 段。**默认按"交给下一个 agent"来写**，不区分给人还是给 agent ——
写给 agent 的标准更严（不能靠人脑补上下文），满足它也就同时满足了人读的需要。

| 段落 | 内容 |
|---|---|
| 目标与现状 | 原本要做什么，现在实际是什么状态 |
| 已改动 | 动了哪些文件、为什么，不要贴 diff |
| 关键决策与理由 | 做了什么选择、为什么、否决了哪些方案；含"看起来像 bug 其实是故意"的陷阱 |
| 未完成 / 已知问题 | 明确列出，并给出下一个具体动作 |
| 验证方式 | 怎么验证：具体命令 + 预期输出 |

Foreman 对交接文档做 lint：缺段落、段落为空、或「验证方式」里没有可执行命令，
则核实态判为 `unsubstantiated`。把"写好交接文档"变成硬约束，而不是道德劝说。

## 8. 功能清单

### MVP

- 前端新建任务：填写目的/背景/验收标准/约束，选目标 repo、记忆 repo、知识库，各字段支持「使用已有设置」
- 知识库索引：扫描 `base/` 与 `projects/`，生成条目清单供提示词引用
- 提示词拼接：四部分合成（含协作规范），一键复制
- **提示词模板可编辑**：内置默认模板，允许使用者修改
- 记录基线 commit
- 看板视图：任务卡片按状态分列，同时显示声明态与核实态
- 任务详情：TASK.md 渲染、TODO 完成度、STATUS.json 原始值、`question` 内容
- **commit 级变更展示**：基线之后的 commit 列表，可展开看 diff
- 核实引擎：扫描目标 repo git 历史，推导核实态
- 交接文档 lint：校验 HANDOFF.md 必填段落
- 冲突高亮：「声称完成 + 零 commit」等矛盾组合显著标出
- 最后活动时间显示
- 手动刷新 + 定时轮询

### 后续

- TODO/DONE 实时更新（文件监听而非轮询）
- 多 repo 任务（一个任务关联多个 repo，以默认 repo 为准）
- 任务历史时间线（基于信号文件的 git 历史回放状态变迁）
- 英文界面与文档

## 9. 前端

要求：**好看且简洁**。具体落地为：

- **无构建步骤**：服务端渲染 + 少量原生 JS，不引入 React/Vue 或打包链，与"无 DB、简单"的整体取向一致
- 手写 CSS，一套 design token（间距、字号、颜色、圆角）统一视觉
- 中性底色 + 少量语义化强调色；状态颜色固定语义（已验证 / 存疑 / 自相矛盾 / 失败）
- commit hash、diff、文件路径用等宽字体
- 信息密度优先：一屏尽量看到全部任务的真实状态，不靠动画和装饰撑场面
- 键盘可达；颜色之外同时用文字标注状态（不依赖颜色单独传达信息）
- 界面文案集中管理，为后续英文适配留出接口

## 10. 技术栈

- Node.js
- 无数据库，git + JSON + Markdown 存储
- 服务端渲染 + 原生 JS 前端，无打包工具
- 读取 git 通过命令行 git 调用
