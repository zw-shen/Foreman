# Foreman 产品与功能定义

> 更好地管理你的大模型，而不是盲目听信它们。

本文档描述 Foreman 当前的实际形态。实现与本文档一致；有出入时以代码为准。

当前阶段以中文为主，英文版待设计成熟后再补。界面文案集中管理，预留多语言适配空间。

---

## 1. 产品定义

Foreman 是一个 **git-backed 的 AI coding agent 监工看板**。

它解决一个具体问题：agent 说"我做完了"，但你无法判断这句话是真的。
Foreman 的做法是不采信自我汇报，而是去看 agent 在 **context repo** 里究竟留下了什么 ——
真实的 commit、约定格式的状态文件、以及一份结构化的交接文档。

**使用者**：同时指挥多个 coding agent、需要快速判断"哪个任务真的推进了、哪个在原地打转"的开发者。

## 2. 最重要的一件事：Foreman 不是 AI

Foreman 是一个**对 agent 产出做反应的程序**。它不调用模型、不读你的代码、不分析 diff、不做推断。

由此推出整个产品的形态：

- agent 做了什么、改了哪些文件、为什么这么改，**必须由 agent 自己写成文字**，
  否则在 Foreman 里等于没发生。
- Foreman 负责的是：读取约定位置的文件、用 git 事实对照 agent 的声明、把结果渲染出来。
- 需要更详细的改动说明时，由**人发起**，Foreman 生成一段追加提示词，agent 写下来，Foreman 渲染。

## 3. 非目标

- **不是调度系统。** 不启动 agent、不管理进程、不做并发控制或任务认领。
- **不是 agent 运行时。** 不代理、不转发、不拦截 agent 与模型之间的请求。
- **不读你的代码仓库。** Foreman 只看 context repo。
- **不写 context repo。** 里面的文件全部由 agent 创建和维护。
- **不做数据库。** 无 DB，状态来自 git 和文件。
- **不设运行超时。** 任务可以无限期运行，不会因为"太久没动静"被判失败。
- **不做二次 LLM 诊断。** 失败原因由 agent 自己写。

Foreman 自己写的东西只有：任务定义、基线 commit、生成的提示词，全部落在自己的 `data/` 目录里。

## 4. 只有一个仓库：context repo

Foreman 全局只认一个仓库，所有任务共用，在设置页配置一次。它同时承担三个角色：

```
context repo/
├── base/       通用知识，跨项目复用
├── projects/   项目知识，按项目分目录
└── tasks/      任务记录，按任务 id 分目录
```

填 **git 地址**或**本地路径**都可以。

### 4.1 context 本地位置

Foreman 通过一个**固定且不可配置**的位置访问它：

```
<Foreman 安装目录>/data/context
```

正因为位置固定，任务里才不需要再记任何路径。

这个位置由 **agent 按提示词自己接上**，Foreman 不代建：

- 填的是本地路径 → `ln -s <路径> data/context`
- 填的是 git 地址 → `git clone <地址> data/context`

提示词要求 agent **先检查是否已存在，已存在就直接用，不存在才创建**。
Foreman 生成提示词时会实测该位置状态并写进提示词，省得 agent 猜。

`ensureDirs()` 特意**不预建**这个目录 —— 否则 agent 的"已存在就用"判断会被一个空目录骗过。

### 4.2 隔离

`data/` 整体在 `.gitignore` 里。所以 context repo 的地址（存在 `data/settings.json`）、
任务数据、以及那个软链本身，都不会进入本公开仓库。

## 5. 核心原则：声明 ≠ 事实

| | 来源 | 可信度 |
|---|---|---|
| **声明态** | agent 写进 `STATUS.json` | 不可信，仅作为线索 |
| **核实态** | Foreman 从 context repo 的 git 历史推导 | 事实 |

看板同时展示两层。两者冲突时，冲突本身就是最重要的信息。

**已知取舍**：核实依据是"agent 有没有真的往 context repo 写下东西并提交"，
而不是代码改动本身。所以一个编造了漂亮交接文档的 agent 能通过核实。
这是"Foreman 不读代码"换来的代价。

## 6. 状态模型

### 6.1 声明态（agent 写入，Foreman 去读）

| 值 | 看板显示 | 含义 | 人要做什么 |
|---|---|---|---|
| `working` | 进行中 | 正在干活 | 不用管 |
| `done` | 完成 | 整个任务完成，不打算继续 | 去核实 |
| `awaiting_review` | 完成等待验收 | 阶段性完成，要人点头再继续 | 去看代码、给结论 |
| `awaiting_input` | 等待回答 | 卡住了，必须先得到回答 | 去回话 |
| `failed` | 失败 | 放弃，必须附 `reason` | 去看原因 |

`awaiting_review` 与 `awaiting_input` 是原「完成等待回复」拆开的结果 ——
两者要人做的动作完全不同，拆开后看板上一眼就知道该干嘛。

`awaiting_input` 必须写 `question`，它会直接显示在看板卡片上，你能当场回话。

### 6.2 核实态（Foreman 推导）

| 值 | 显示 | 判定依据 |
|---|---|---|
| `verified` | 已验证 | 声明完成，且基线之后有真实提交产出，且交接文档校验通过 |
| `unsubstantiated` | 存疑 | 声明完成，但零提交产出 / 交接文档不合格 |
| `contradicted` | 自相矛盾 | 声明失败，但基线之后有可观产出（东西可能还有用） |
| `error` | 无法核实 | context 位置不存在 / 不是 git 仓库 / 基线 commit 不可达 |

`verified` 与 `unsubstantiated` 同时适用于 `done` 和 `awaiting_review` ——
"阶段性完成、请你验收"同样应该有东西可看。

### 6.3 最后活动时间（不做判定）

不设超时状态，但每个任务显示最后活动时间（最近一次 commit 或状态文件更新距今多久）。

这是有意的取舍：agent 崩溃时不会自己写 `failed`，看板上它和一个正常长跑的任务无法区分。
硬超时会制造假警报，所以 Foreman 不替你下结论，只把"多久没动静"摆出来。

## 7. 任务

### 7.1 新建

任务在前端新建，只填任务本身：**标题、目标、背景、验收标准、约束**。没有任何路径字段。

提交时 Foreman 记录 context repo 当前的 HEAD 作为**基线 commit**，
之后"哪些产出属于这个任务"就是"基线之后的 commit"。

context 未配置或未就位时**不阻止**创建，只是记不到基线，核实态显示「无法核实」并说明原因。

### 7.2 任务文件

由 agent 创建在 context repo 内：

```
tasks/<task-id>/
├── TASK.md      任务契约
├── TODO.md      待办清单（checkbox）
├── STATUS.json  当前状态（机器读取）
├── HANDOFF.md   交接文档
└── CHANGES.md   改动明细（仅在人要求时才写）
```

这些文件随 context repo 一起被 git 跟踪，所以**状态变更历史免费获得**，而且难以伪造 ——
想谎报"一路顺利"，得连 commit 历史一起编。

### 7.3 `STATUS.json`

```json
{
  "task_id": "string",
  "state": "working | done | awaiting_review | awaiting_input | failed",
  "updated_at": "ISO-8601",
  "reason": "state=failed 时必填",
  "question": "state=awaiting_input 时必填"
}
```

不设"agent 自报 commit 列表"字段：产出归属由基线推导，不采信 agent 的说法。

### 7.4 `HANDOFF.md`

5 个必填一级标题，按"交给下一个 agent 接手"的标准写：

| 段落 | 内容 |
|---|---|
| 目标与现状 | 原本要做什么，现在实际什么状态 |
| 已改动 | 每个文件写清：改了什么 / 为什么 / 意义影响 |
| 关键决策与理由 | 选择、理由、否决的方案、"看着像 bug 其实是故意"的陷阱 |
| 未完成 / 已知问题 | 明确列出，并给出下一个具体动作 |
| 验证方式 | 可执行命令 + 预期输出 |

**「已改动」是重点** —— Foreman 看不到代码，这一段是唯一的信息来源，所以要求逐文件写三件事。

Foreman 会 lint：段落是否齐全、是否为空、「验证方式」里是否包含可执行命令。
不合格会让任务被判**存疑**，即使声明了完成。

段落解析有个细节：必填段落下面允许有更深层级的小标题（`已改动`下面按 `## <文件路径>` 分节）。
解析时先找出必填段落所用的最浅标题层级，只在该层级切分，更深的算正文 ——
否则照规范写的 agent 反而会被判"段落为空"。

### 7.5 改动明细（按需索取）

平时不需要写 `CHANGES.md`。任务页有「要求 agent 说明改动明细」入口：
点击生成一段追加提示词 → 你贴回 agent 会话 → agent 写 `CHANGES.md` 并提交 → Foreman 渲染。

## 8. 提示词

Foreman 不启动模型。它生成提示词，你自己开会话贴进去。

提示词由模板拼接，占位符如下：

| 占位符 | 内容 | 可改性 |
|---|---|---|
| `{{RULES}}` | 对 agent 的通用要求 | 设置页自由编辑，有实质默认值 |
| `{{KNOWLEDGE_INDEX}}` | 知识条目索引 | 自动扫描 |
| `{{TASK_INFO}}` | 本任务的目标、背景、验收标准、约束 | 建任务时填 |
| `{{REPOS}}` | context 地址、本地位置、基线 commit | 自动 |
| `{{PROTOCOL}}` | Foreman 的机制约定 | 由 Foreman 生成，保证路径与状态取值不写错 |

模板本身可编辑（决定顺序与措辞）。删掉 `{{PROTOCOL}}` 会让整套约定失效。

设置页提供**完整提示词预览**：用一个示例任务拼出实际结果，让 `{{PROTOCOL}}` 展开后的内容可见。

### 8.1 知识库按需读取

提示词里**不塞知识库全文**，只给条目索引（有哪些条目、各自讲什么）和位置，
由 agent 自己判断读哪几篇。避免上下文被无关内容占满，也让知识库能长大而提示词不跟着膨胀。

同时要求 agent 在遇到值得沉淀的信息时新增条目：通用的放 `base/`，项目相关的放 `projects/<项目名>/`。
一次性的临时结论不要写进 `base/`。

### 8.2 及时提交推送

context repo 是 git 仓库时，提示词要求 agent 只要写了东西就及时 commit 并 push ——
它跨任务共享，留在本地等于没沉淀；而且 Foreman 靠 commit 核实，
**攒着不提交等于在 Foreman 眼里什么都没干**。push 失败不许静默忽略，要写进交接文档。

context 只是普通目录（非 git）时不提 push，改为提示"无法用 commit 核实"。

## 9. 存储

无数据库。

```
Foreman/
├── src/            应用代码（入库）
├── docs/           文档（入库）
├── .gitignore
└── data/           ← 整体 gitignore
    ├── settings.json   全局配置：context 地址、通用要求、提示词模板
    ├── tasks/          任务数据：task.json + PROMPT.md
    └── context/        context repo 的固定接入位置（由 agent 创建）
```

路径全部运行时推导：代码位置来自 `import.meta.url`，家目录来自 `os.homedir()`，
没有任何硬编码。换一台机器 clone 到别的目录同样成立。

界面上显示路径时把家目录缩写成 `~`；**提示词里保留真实绝对路径**，因为 agent 要拿它访问文件。

## 10. 界面

- **无构建步骤**：服务端渲染 + 少量原生 JS，不引入前端框架或打包链
- 手写 CSS，一套 design token 统一视觉
- 状态颜色语义固定；颜色之外同时用文字标注，不依赖颜色单独传达信息
- commit hash、diff、路径用等宽字体
- 信息密度优先，看板按"人需要做什么"的紧急程度排列：
  等待回答 → 完成等待验收 → 完成 → 失败 → 进行中 → 未上报
- 路径输入支持**浏览本地目录**并可新建目录（可选同时 `git init`）

## 11. 技术栈

- Node.js，**零 npm 依赖**，只用内置模块
- 无数据库，git + JSON + Markdown
- 服务端渲染 + 原生 JS，无打包工具
- 读取 git 通过命令行调用，一律 `execFile` + 参数数组，不经过 shell

## 12. 安全

- **无鉴权**。默认只监听 `127.0.0.1`，不要暴露到网络。
- 目录浏览接口会暴露本机目录结构，新建目录是写操作 —— 更不能对外开放。
- 所有外部内容（context repo 里的文件、diff、目录名）进入 HTML 前一律转义；
  前端渲染 diff 与目录名用 `textContent` 构建 DOM，不拼 HTML。
- 任务 id、commit sha、新建目录名都走白名单校验，防目录穿越与注入。

## 13. 开放问题

- 知识库索引的条目说明取自一级标题；是否改为要求 front-matter 摘要？
- agent 往知识库新增条目后是否需要人工确认（防止一次性结论被沉淀成"通用知识"）？
- 一个 context 本地位置同时只能接一个仓库。若要让不同任务用不同 context repo，需要改成按任务分目录。
